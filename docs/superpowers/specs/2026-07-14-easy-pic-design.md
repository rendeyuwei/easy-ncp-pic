# EasyPic Web 照片滤镜项目设计规格

日期：2026-07-14

## 1. 产品概述

EasyPic 是一个面向普通用户的 Web 照片滤镜工具。用户上传一张 JPG 或 PNG 照片后，可直接浏览由管理员精选并发布的 Nikon `.ncp` 滤镜效果，对比原图，并以原始分辨率下载处理结果。

照片解码、滤镜预览和原图导出全部在用户浏览器内完成。服务器不接收或保存用户照片，只负责提供页面、公开滤镜参数和管理员功能。这一架构适合资源有限的服务器。

### 1.1 目标

- 普通用户无需注册即可完成“上传照片 → 选择滤镜 → 下载照片”。
- 滤镜切换直观、快速，并提供真实的原图/效果对比。
- 只有一个管理员账号可上传、编辑、排序、启用或停用滤镜。
- 支持管理员手动上传从合法来源获得的 `.ncp` 文件。
- 下载结果保持输入照片的像素尺寸。
- 服务器端保持轻量，适合直接运行 Node.js 的低配服务器。

### 1.2 第一版不包含

- RAW、NEF、HEIF 输入。
- `.np2`、`.np3` 滤镜。
- 多张照片批量处理。
- 普通用户账号、云端相册和跨设备同步。
- 自动抓取或同步 nikonpc.com。
- 与 Nikon 相机或 NX Studio 的逐像素一致性承诺。

## 2. 核心技术决策

- 前端：Vite 8.x、React 19.x、TypeScript。
- UI：shadcn/ui；所有核心交互均使用可访问的标准组件。
- 动效：按需引入少量 React Bits 组件，仅用于上传入口、页面过渡和滤镜列表反馈。
- 路由：TanStack Router 客户端路由；不采用 TanStack Start 服务端渲染。
- 请求状态：TanStack Query，用于公开滤镜数据和后台管理请求。
- 后端：Fastify 轻量 Node.js API；生产环境的前端静态文件由 Nginx 提供。
- 数据库：SQLite + `better-sqlite3`，开启 WAL 和外键约束。
- 图片处理：WebGL 优先，Canvas 2D 回退；耗时工作由 Web Worker 承担。
- 部署：Node.js 22 LTS、PM2、Nginx、HTTPS，不使用 Docker。
- 包管理：pnpm；提交 lockfile 并固定实际安装版本。

Vite 8 要求 Node.js 20.19+ 或 22.12+。生产环境统一使用 Node.js 22 LTS，避免开发与部署运行时差异。

## 3. 用户角色与操作流程

### 3.1 普通用户

1. 打开首页，看到明确的 JPG/PNG 拖放上传区及“照片不会上传服务器”提示。
2. 选择一张照片后，浏览器读取文件、修正 EXIF 方向并生成预览。
3. 页面进入沉浸式编辑器：桌面端左侧为大图，右侧为滤镜栏；移动端滤镜栏移动到照片下方。
4. 浏览器使用用户照片的小尺寸副本生成滤镜缩略图。
5. 用户按分类浏览并点击滤镜，主预览立即更新。
6. 用户拖动分割线对比原图与效果；按住指定控件时可临时查看完整原图。
7. 用户可调整滤镜强度，默认 100%。不调整强度即可完成一键套用。
8. 用户选择 JPG 或 PNG 并点击下载。
9. 浏览器对原始像素尺寸执行同一处理管线，显示进度并保存结果。

### 3.2 管理员

1. 访问 `/admin`，使用单一管理员账号和密码登录。
2. 查看滤镜列表、状态、分类和排序。
3. 上传一个 `.ncp` 文件。服务端验证长度、签名、版本和字段边界。
4. 解析成功后显示文件内名称、基础 Picture Control、曲线摘要和可识别参数。
5. 管理员填写中文名称、分类和简短说明，设置排序和启用状态。
6. 保存后，公开接口立即返回新滤镜，无需重新构建或重启服务。
7. 管理员可编辑、停用或删除滤镜；删除需二次确认。

## 4. 界面与视觉设计

### 4.1 核心布局

采用已确认的“沉浸式编辑器”方案：照片是页面最重要的视觉对象，滤镜控件不会覆盖照片的重要区域。

- 桌面端：顶部简洁导航；主区域为大图预览；右侧固定宽度滤镜栏。
- 移动端：大图在上；分类和横向滤镜列表在下；下载按钮保持清晰可见但不遮挡图片。
- 首页：单一主操作为上传照片，不放置营销型复杂模块。
- 管理端：使用 shadcn/ui 表格、表单、对话框、提示和下拉菜单。

### 4.2 设计系统与动效

- 默认采用深色摄影工作台风格，同时支持浅色主题。
- shadcn/ui 负责按钮、输入、对话框、Toast、表格、标签、滑块和菜单。
- React Bits 动效必须懒加载，不参与照片像素处理。
- 照片预览区域不使用持续背景动画，以免影响用户判断颜色和明暗。
- 尊重 `prefers-reduced-motion`；启用减少动态效果时移除非必要动画。
- 所有关键功能可通过键盘操作，并具有清晰焦点样式和可读标签。

## 5. 系统架构与模块边界

### 5.1 `web-app`

负责普通用户页面、文件选择、编辑器状态、滤镜选择、对比和导出控制。它只依赖公开滤镜 API 和 `image-engine`，不接触管理员凭据。

### 5.2 `admin-app`

负责登录和滤镜管理界面。它调用受保护的管理 API，不直接访问 SQLite 或文件系统。

### 5.3 `ncp-parser`

负责验证 NCP 二进制并输出版本化的统一滤镜对象。解析器不执行图片处理，也不依赖 HTTP 或数据库。相同输入必须产生确定性输出。

### 5.4 `image-engine`

负责照片方向修正、预览缩放、缩略图、滤镜计算、强度混合和原尺寸导出。预览和导出共用同一参数模型与着色器逻辑，避免两套算法产生差异。

### 5.5 `api-server`

负责静态资源、公开滤镜接口、管理员认证、上传限制、安全响应头、管理接口和健康检查。API 不提供用户照片上传接口。

### 5.6 `database`

负责 SQLite schema、迁移、事务和备份约定。业务模块通过存储接口访问，不在路由处理器中散落 SQL。

## 6. 数据流

### 6.1 公开滤镜

1. 管理员上传 NCP。
2. API 验证文件并调用 `ncp-parser`。
3. 原始二进制和解析后的版本化 JSON 在同一事务中写入 SQLite。
4. 公开接口只返回已启用滤镜的展示信息和解析参数。
5. 浏览器缓存滤镜数据，并将参数传入 `image-engine`。

### 6.2 用户照片

1. 浏览器通过 File API 读取本地照片。
2. `createImageBitmap` 或兼容路径完成解码和方向处理。
3. 小尺寸像素送入 WebGL/Worker 生成主预览和缩略图。
4. 原始文件引用只保存在当前浏览器内存中。
5. 下载时重新解码原始尺寸，分块或分阶段处理并生成 Blob。
6. 页面卸载后释放 Object URL、ImageBitmap、纹理和 Worker 内存。

## 7. SQLite 数据设计

### 7.1 `admins`

- `id`
- `username`，唯一
- `password_hash`，Argon2id
- `created_at`
- `password_changed_at`

第一版只创建一个管理员，但表结构不将账号写死在代码中。

### 7.2 `filters`

- `id`，稳定的 UUID
- `slug`，唯一公开标识
- `display_name`
- `source_name`，NCP 内置名称
- `description`
- `category_id`
- `sort_order`
- `is_enabled`
- `ncp_blob`，原始二进制
- `ncp_sha256`，用于去重和审计
- `parser_version`
- `parsed_json`
- `created_at`
- `updated_at`

### 7.3 `admin_sessions`

- `id`
- `admin_id`
- `token_hash`，仅保存随机会话令牌的哈希
- `csrf_secret`
- `expires_at`
- `created_at`
- `last_seen_at`

### 7.4 `filter_categories`

- `id`
- `name`
- `slug`
- `sort_order`
- `is_enabled`

SQLite 使用 WAL、`foreign_keys=ON` 和显式迁移。数据库文件以及相关运行配置形成一个可备份的数据目录。

## 8. API 设计

### 8.1 公开接口

- `GET /api/filters`：返回启用的分类和滤镜参数，支持 ETag/缓存。
- `GET /api/health`：返回进程和数据库健康状态，不暴露敏感配置。

### 8.2 管理接口

- `POST /api/admin/session`：登录。
- `DELETE /api/admin/session`：退出。
- `GET /api/admin/filters`：完整滤镜列表。
- `POST /api/admin/filters`：上传并创建滤镜。
- `PATCH /api/admin/filters/:id`：编辑展示信息、分类、排序和状态。
- `DELETE /api/admin/filters/:id`：删除滤镜。
- `GET /api/admin/categories`、`POST /api/admin/categories`、`PATCH /api/admin/categories/:id`、`DELETE /api/admin/categories/:id`：分类管理。

管理写接口要求有效会话、同源请求和 CSRF 防护。错误响应采用统一结构：`code`、用户可读 `message` 和可选字段错误。

## 9. NCP 解析设计

NCP 是 Nikon Picture Control 的二进制格式。Nikon 公开说明其功能和自定义曲线行为，但未公开完整二进制布局，因此实现采用“已验证字段 + 严格边界检查 + 样本回归测试”的方式。

### 9.1 已验证样本

#### `PICCON02.NCP`

- SHA-256：`ed53222f4a2329c3f42a2dd6391b4b62d1214b1e3eac917d9bd11a8f22f9e43f`
- 长度：638 字节
- 名称：Fuji Astia
- 基础模式：Neutral
- 自定义曲线：启用
- 锐化：2；饱和度：0；色相：0
- 控制点：`(0,0) (52,53) (169,178) (250,245) (252,248) (255,255)`

#### `PICCON33.NCP`

- SHA-256：`5a3e2e9a768234f0fa653f1fc50eef3993118788737e57fe4bbd8d219fa8bc12`
- 长度：638 字节
- 名称：SHING TokugawaTone2
- 基础模式：Monochrome
- 自定义曲线：启用
- 锐化：2；滤色类型：83；调色类型：84；调色强度：2
- 控制点：`(0,85) (63,98) (125,194) (188,224) (249,232)`

### 9.2 已验证布局

- `0x00..0x03`：ASCII `NCP\0`。
- `0x04..0x07`：格式主版本，样本为大端序数值 1。
- `0x08..0x0B`：头部相关长度，样本为 `0x24`。
- `0x0C..0x0F`：ASCII 版本 `0100`。
- `0x10..0x23`：最多 20 字节、NUL 填充的名称。
- `0x24` 起：基础 Picture Control 与调整字段区域。
- `0x3E`：样本中的自定义曲线启用标志。
- `0x3F`：曲线 gamma 偏移；`0x0F` 对应 1.15，`0x00` 对应 1.00。
- `0x40`：控制点数量。
- `0x41` 起：控制点的 8-bit `x,y` 对。
- `0x78` 起：257 个大端序 16-bit LUT 值，使用 15-bit 范围 `0..32767`。
- LUT 后四字节：保留字段，当前样本均为零。

基础模式、彩色调整、黑白滤色和调色字段使用枚举或以 `0x80` 为中心的编码。实现时每个映射必须由具名 fixture 验证；未知枚举不能静默猜测。后台对未知但结构安全的文件显示“不支持的 NCP 变体”，不允许发布。

### 9.3 统一解析结果

解析器输出至少包括：

- `schemaVersion`
- `sourceFormat` 和 `sourceVersion`
- `sourceName`
- `basePictureControl`
- `sharpening`
- `saturation`、`hue`
- `monochromeFilter`、`toningType`、`toningStrength`
- `customCurve.enabled`
- `customCurve.gamma`
- `customCurve.controlPoints`
- `customCurve.lut257`，归一化到 `0..1`
- `warnings`

解析器始终先验证总长度、字段边界、点数量、点顺序和 LUT 数值范围，再构造结果。

## 10. 图片处理管线

### 10.1 输入规范化

- 支持 `image/jpeg` 和 `image/png`。
- 解码后统一为浏览器管理的 sRGB 像素并修正 EXIF 方向。
- 默认预览最长边为 2048 像素；低内存设备降为 1280 像素，原始尺寸元数据保持不变。
- 第一版拒绝超过 10000 像素单边或 8000 万总像素的图片，防止解压缩炸弹和浏览器崩溃。

### 10.2 滤镜顺序

```text
输入 sRGB
→ 基础彩色/黑白模式
→ 257 点 NCP 曲线
→ 饱和度与色相
→ 黑白滤色与调色（如存在）
→ 锐化
→ 与原图按强度混合
→ 编码导出
```

- 257 点 LUT 作为 1D 浮点纹理或等价查找表使用，不压缩成少量控制点。
- 彩色模式对 RGB 通道使用同一主曲线；运算中间值使用浮点并在最终输出时裁剪。
- 黑白模式使用明确、可测试的亮度权重，再应用滤色和调色。
- 锐化使用受限制的 Unsharp Mask，强度由 NCP 锐化值映射并限制光晕。
- 强度滑块在原图与完整滤镜结果之间混合，默认 100%。
- WebGL 与 Canvas 回退必须共享参数模型，并通过像素容差测试保证接近。

### 10.3 导出

- 默认沿用输入格式：JPG 导出 JPG，PNG 导出 PNG；用户可切换。
- JPG 默认质量为 0.92，并在下载对话框明确显示。
- 保持原始像素宽高；第一版不承诺保留 EXIF、GPS 或其他元数据。
- 超大图片按设备能力采用分块策略；若仍无法完成，提示用户选择缩小尺寸或 JPG，而不清空编辑状态。

## 11. 安全与隐私

- 用户照片没有服务端上传路由，服务器日志中不出现照片内容或本地文件名。
- 管理员密码使用 Argon2id，参数根据部署服务器基准选择安全且可接受的成本。
- 会话使用 Secure、HttpOnly、SameSite Cookie；生产环境仅通过 HTTPS。
- 登录接口限速，连续失败触发短时限制。
- NCP 上传请求体上限为 64 KiB；第一版只接受签名、版本和 638 字节布局均通过验证的 NCP 1.00 文件。
- API 设置 CSP、HSTS、`X-Content-Type-Options`、合理的 `Referrer-Policy` 等安全头。
- SQL 全部参数化；管理输入在输出时按上下文转义。
- 管理员只上传自己制作或有权公开使用的滤镜。系统不自动抓取第三方网站。

## 12. 错误与恢复

- 损坏或未知 NCP：拒绝发布，显示具体但不泄露内部堆栈的错误。
- 重复 NCP：按 SHA-256 提醒管理员，避免误建重复记录。
- 图片格式伪装：以实际解码结果为准，失败时给出可操作提示。
- WebGL 不可用或上下文丢失：自动切换 Canvas/Worker 回退并提示性能可能降低。
- 设备内存不足：降低预览尺寸；导出失败时保留编辑状态并提供替代选项。
- API 暂时不可用：已加载照片继续留在浏览器；公开滤镜列表可使用短期缓存。
- SQLite 写入失败：事务回滚，原记录保持不变。

## 13. 测试与验收

### 13.1 单元测试

- 两个已验证 NCP fixture 的名称、模式、参数、控制点和 257 点 LUT。
- 截断文件、错误签名、错误版本、越界点数、无序控制点和未知枚举。
- 曲线归一化、颜色转换、黑白滤色、调色、锐化和强度混合。
- SQLite 迁移和存储接口。

### 13.2 集成测试

- 管理员登录、退出、Cookie、限速和未授权访问。
- NCP 上传、重复检测、保存、编辑、上下架和删除。
- 公开接口只返回启用滤镜，并正确应用 ETag。
- 数据库事务失败时不产生半成品记录。

### 13.3 浏览器端到端测试

- 上传 JPG/PNG、选择滤镜、生成缩略图、原图对比和下载。
- 下载文件可重新解码，且像素宽高与原图一致。
- 桌面和移动布局。
- 深色/浅色主题及减少动态效果模式。
- WebGL 主路径和 Canvas 回退路径。

### 13.4 视觉与性能验收

- 已缓存滤镜的预览切换不触发网络请求。
- 预览处理不长期阻塞主线程，加载和导出均显示进度。
- React Bits 不进入首屏关键编辑路径；非必要动效可完全关闭。
- 公开页面不上传照片，可通过网络测试断言验证。
- 服务器空闲资源主要由 Node.js 进程和 SQLite 占用，不运行独立数据库服务。

## 14. 部署与运维

- Vite 生成静态资源，由 Nginx 提供并设置内容哈希长期缓存；Fastify 只处理 `/api`。
- Node API 监听本机端口，由 PM2 启动、自动重启并保存日志。
- Nginx 终止 TLS，代理 `/api`，并限制上传请求大小。
- 环境变量保存会话密钥、初始管理员配置和数据目录路径；不提交真实秘密。
- SQLite 数据目录位于发布目录之外，更新代码不会覆盖数据。
- 每日备份 SQLite 数据目录，保留多份轮换；备份过程使用 SQLite 安全快照方式。
- 提供数据库迁移命令、健康检查和部署回滚说明。
